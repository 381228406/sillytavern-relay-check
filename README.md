# 中转检测

SillyTavern 的 UI 扩展（不是 server plugin），用来辅助判断当前 Chat Completion / OpenAI 兼容中转是否能连上、有没有被路由或换模型，以及接口现在正不正常。

作者：大总管  
版本：1.0.0  
许可：AGPLv3（与酒馆生态一致）

## 安装

任选一种方式，然后**重载酒馆页面**。

1. **从 URL 安装**（如果你拿到了本扩展的 Git 仓库地址）  
   扩展 → 安装扩展 → 从 URL 安装，粘贴仓库地址。

2. **手动安装（给所有用户）**  
   把本文件夹放到：

   `public/scripts/extensions/third-party/sillytavern-relay-check`

   注意文件夹名必须是 `sillytavern-relay-check`。若你拿到的是 zip，解压后根目录就是 `manifest.json`、`index.js` 这些文件，把它们整个放进上述目录即可。

3. **手动安装（仅当前用户）**  
   放到当前用户的扩展目录，例如：

   `data/<用户名>/extensions/sillytavern-relay-check`

安装后在「扩展」里启用「中转检测」。设置面板在扩展设置右侧栏，顶栏连接状态附近会多一个小角标。

## 功能

- **一键检测当前连接**（设置面板按钮，或斜杠命令 `/relaycheck`、`/中转检测`）
  - 走酒馆自己的后端代理访问 `/status`（模型列表 / 连通）和一次极短生成。
  - 看能不能连上、鉴权是否通、延迟、HTTP / 429 / 超时。
  - 模型列表能否拿到、当前模型在不在列表里。
  - 对比「请求的模型名」和回包里的 `model`。
  - 看 usage 是否存在、是否和估算输入大致相当；标出厂商特有字段（如 Gemini usageMetadata、Anthropic usage / 思考块签名、cache 字段）。
  - 看响应 `id` 前缀是否像常见家族（`chatcmpl-` / `msg_` / `gen-` 等）。
- **深度检测**（另开按钮，或 `/relaycheck deep=on`）
  - 会多耗额度，开始前会确认。
  - 短码回显、约 2k–4k 的上下文针测（在长 prompt 头部埋随机码让模型读回，**不会打 100k+ 超长上下文**）。
  - 流式 vs 非流式是否都能用、回包模型是否一致。
  - 多次短探针的模型名 / 延迟是否明显飘动。
- **自动监控**（设置里可关，默认开）
  - 观察你平时正常生成时，酒馆后端代理已经拿到的回包元数据（model / usage / id / 延迟）。
  - **不会额外打探测，不额外消耗额度。**
  - 模型不一致、延迟明显异常、接口报错时，角标更新，并用 toastr 提醒（同一类问题大约一分钟内不重复刷）。
- **结果面板**
  - 清楚分成：正常 / 同系列分流 / 疑似路由或换模型 / 接口异常。
  - 每项有短说明和具体数据（延迟 ms、请求模型 vs 回包模型、usage）。
  - 保留最近几次检测记录。点顶栏角标可查看最近一次结果。

## 怎么读结果

- **正常**：能连上，探测生成成功，回包模型与请求一致（或回包没给模型名）。
- **同系列分流**：例如 `gemini-4-argon` → `gemini-4-argon-high`，或带日期 / preview / fast 这类后缀。会告知，但**不算换模型**。
- **疑似路由或换模型**：回包模型跨家族，或多次探针的模型名差很多。
- **接口异常**：连不上、鉴权失败、429、超时、生成失败等。

拿不到的字段会写「无法获取」，不会假装检测过。模型在正文里自称是谁，中转可以改，**不当作证据**。

## 一键 vs 深度会消耗什么

| 项目 | 大约消耗 |
| --- | --- |
| 一键检测 | `/models` 或等价状态检查（通常不计生成额度）+ **1 次**极短生成（大约十几 token 的输出） |
| 深度检测 | 一键检测之外，再加回显、针测、非流式对比、流式对比，大约再 **4 次**短请求。针测输入大约 2k–4k token，请注意套餐输入额度 |
| 自动监控 | 不额外发请求 |

请不要在额度所剩无几时空刷深度检测。

## 技术说明

- 只面向 **Chat Completion**（包括 Custom / OpenAI 兼容中转，如常见的 Logits Token、Router One 一类网关）。如果当前是 Text Completion 或其他 API，会友好提示，不会崩溃。
- API 密钥在酒馆服务端 Secrets 里。扩展**不会**让你再贴一次 key，也**绝不会**把 key、密码或完整 prompt 发到 Veridrop 或任何第三方。
- 优先使用 `SillyTavern.getContext().generateRawData()`；没有该接口时，降级为直接请求酒馆的 `/api/backends/chat-completions/generate`。两条路都走后端代理。
- 上游 HTTP 响应头不会被酒馆原样传回前端，所以响应头一律记为「无法获取」。
- 自动监控：普通聊天的 `MESSAGE_RECEIVED` / `GENERATION_ENDED` **拿不到**上游回包里的 `model` / `usage`（消息上的 `extra.model` 是请求时选中的模型，`token_count` 是本地估算）。因此扩展会观察发往酒馆后端 `/api/backends/chat-completions/generate` 的响应元数据，只记录 model、usage、id、延迟，不保存对话正文。

## 限制（请务必读）

1. **不能 100% 证明这是官方真模型。** 尤其 Gemini、GPT 没有 Claude 那种较难伪造的思考签名。
2. 聪明的中转可能只把探测请求送到真接口，平时聊天仍走别的上游。自动监控能降低这种风险，但无法彻底杜绝。
3. 缺少 usage 或 `id` 前缀不标准，在很多兼容中转上很常见，只能当弱信号。
4. 针测失败更常见的原因是指令遵循差或上下文被截断，不要单独当成「假模型」。
5. 需要 SillyTavern 较新的版本（建议 1.13+）。更旧的版本会尽量降级，但 `generateRawData`、新版斜杠命令或 loader 可能不可用。

## 斜杠命令

```
/relaycheck
/中转检测
/relaycheck deep=on
```

命令会返回一份可给 STscript 使用的文字摘要。
